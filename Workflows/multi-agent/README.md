# 多 Agent 并行编排

## 核心思想

**主 agent 只做调度，子代理各自带干净 context 并行干活。** 主 agent 的价值不在自己干活，而在于把任务切成互不依赖的块、分发给子代理、最后集中收口。

## 为什么有效

- **上下文隔离**：每个子代理的 context 只装自己那一块任务的细节，主 context 只装结论不装过程。三个子代理各读 500 行代码，主 agent 看到的只是三份摘要——上下文预算换来了判断力的续航。
- **墙钟时间**：互不依赖的任务并行后，总耗时约等于最慢的一块，而非总和。
- **新鲜偏见**：子代理没有被主 agent 的推理过程"说服"过，用于调研和审查时盲区更小。

## 两种基本模式

### 扇出调研（读操作，放心并行）

多个只读子代理同时调研不同问题（模块结构 / 兼容性 / 测试缺口），一次拿回多份报告。读操作没有副作用，这是风险最低、收益最直接的并行场景，应当成为处理大代码库的默认动作。

### worktree 并行开发（写操作，严格切分）

```bash
git worktree add ../wt-feature-a -b feat/a   # agent A 的工作区
git worktree add ../wt-feature-b -b feat/b   # agent B 的工作区
```

每个写任务的子代理工作在独立 worktree 中，物理隔离文件系统；各自开发、各自测试全绿、各自提交；最后由主 agent（或人）**集中合并收口**。

合并时冲突是预期行为而非事故：两个 agent 在同一文件的相邻位置各加内容必然冲突。只要切分保证**逻辑独立**，冲突就只是机械的几分钟收口。真正要避免的是两个 agent 修改同一段逻辑——那是切分失败。

## 关键设计点

1. **任务切分先于并行启动**：写操作并行的前提是任务能切成互不依赖的块。切不干净就不要并行——合并地狱比串行慢得多。
2. **并行 agent 更需要提交纪律**：子代理没有全局视野，会做出主 agent 不会犯的错（实战案例：子代理把 `__pycache__` 一并提交）。提交规范、禁止事项必须写进 `AGENTS.md`，而不是靠主 agent 事后叮嘱。
3. **收口权集中**：合并、解决冲突、最终验收只由一个角色（主 agent 或人）执行，绝不让子代理互相合并。

## 什么时候不该并行

- **步骤强耦合**：后一步依赖前一步的产物与决策，串行反而更快——并行只会制造等待和返工。
- **任务太小**：启动子代理有固定的上下文交接成本，几分钟能做完的事不值得编排。
- **需要持续人类判断**：每个子代理都是一次委托，委托的前提是任务能被完整描述。

## 与其他工作流的叠加

- [规格驱动](../spec-driven/) tasks 阶段的 `[P]` 标记就是并行切分单——规格阶段把切分想清楚，并行阶段照单执行。
- 互不依赖的批量任务分组，可以每组起一个 [Ralph 循环](../ralph-loop/)，实现"循环 × 并行"的叠加。
