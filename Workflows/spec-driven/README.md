# 规格驱动开发（Spec-Driven Development）

## 核心思想

**规格文档是唯一事实来源。** 先让 AI 把"要做什么"写成规格，人审规格，AI 再严格按规格实现——实现阶段的 AI 没有自由发挥的空间。

## 为什么有效

机制只有一条：**把人的判断力前置到纠错成本最低的环节**。

- 审一段文字描述的需求，比审一千行代码便宜一个数量级。需求理解错了，改规格是一分钟的事；代码写错了方向，返工是几小时的事。
- LLM 的漂移发生在长链条的实现过程中。规格把"意图"固化在磁盘上，实现 agent 每一步都有锚点校对，跑偏会立刻显形。
- 规格同时是团队的沟通件和归档件，天然解决了"这个需求当时到底怎么定的"。

## 流程

```
constitution → specify → plan → tasks → implement
```

1. **constitution（项目章程）**：整个项目的不可协商原则，一次写好长期复用。如"测试先行""存储格式向后兼容""公开接口必须有类型标注"。它是后续所有阶段的审查基线。
2. **specify（功能规格）**：只写 what 和 why，不写 how。包含用户故事、功能需求、**可测量的成功标准**（"旧数据零迁移"这种一句话需求，会直接变成一条兼容测试）。
3. **plan（技术方案）**：把规格翻译成技术决策——选型、结构、数据流，并逐条对照 constitution 做合规检查。
4. **tasks（任务分解）**：按用户故事分组，每个任务独立可验收；互不依赖的任务标 `[P]`，天然为多 Agent 并行留出接口。
5. **implement（实现）**：严格按 tasks 执行，测试先行——先写红灯测试，再实现转绿。

[`templates/`](templates/) 提供了四个阶段的精简模板，拷进项目即可用。成熟的开源实现参考 [GitHub Spec Kit](https://github.com/github/spec-kit)。

## 关键设计点

- **constitution 要"不可协商"**：写进去的原则必须在 plan 阶段被逐条审查，否则章程只是装饰。
- **成功标准必须可测量**："体验更好"不是标准，"导出一个 10 万行的文件不超过 5 秒"才是。
- **spec 里禁止出现实现细节**：一旦出现"用 Redis 存"，规格就退化成了实现的复述，失去了审查价值——那是 plan 阶段的领地。

## 失败模式与适用边界

| 失败模式 | 表现 | 对策 |
|---|---|---|
| 规格写成实现复述 | spec 里满是函数名和技术选型 | specify 阶段只许写 what/why |
| 章程空转 | plan 阶段不做合规检查 | plan 模板里强制留出 constitution check 表 |
| 杀鸡用牛刀 | 改一行 bug 也走五阶段 | 小修小补直接改，本流程只用于有分量的功能 |

**适合**：重要功能、多人协作、需求复杂且要追溯的场景。
**不适合**：探索性原型（需求本身就是模糊的，先写代码探路）、一次性脚本。

## 与其他工作流的叠加

- tasks 阶段的 `[P]` 标记直接喂给[多 Agent 编排](../multi-agent/)：独立任务并行开发。
- 规格固化的验收标准正是[自主循环](../ralph-loop/)能跑起来的前提——循环需要"可客观验证"，规格恰好提供它。
