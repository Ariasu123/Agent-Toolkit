# 头脑风暴：提问式需求澄清

用户的初始提示词往往只包含部分信息。你的任务是通过**逐轮提问**，把没说清的目的、范围、约束、边界情况问出来，最终形成一份完整的需求描述，经用户确认后再动手。

**核心原则：在用户需求被澄清并确认之前，不写任何代码、不创建任何文件、不调用任何实现类 skill。**

## 流程

### 1. 先摸清现状

提问之前，快速浏览相关的代码、文档、目录结构。答案已经存在于项目里的问题不要问——提问只针对提示词和项目中都找不到答案的信息。

### 2. 逐轮提问，一次一个

- **每条消息只问一个问题**。一个话题没问透就拆成多轮，不要一次抛出问卷式的问题清单。
- **优先选择题**：给出 2~4 个选项，附上你的推荐和理由；开放题只在选项无法穷尽时使用。
- **每轮根据上一回答动态决定下一个问题**，不预设固定的问题列表。
- 用户答得模糊就追问，不要替用户假设。

### 3. 提问围绕五类边界

聚焦补全提示词缺失的信息：

| 维度 | 要探明什么 |
|---|---|
| **目的** | 到底解决什么问题？给谁用？为什么是现在做？ |
| **范围** | 具体做什么？同样重要：明确**不做什么**（non-goals） |
| **约束** | 技术栈、性能、兼容性、预算、时间等硬限制 |
| **边界情况** | 异常输入、极端场景、失败时怎么办 |
| **成功标准** | 怎么算做完了？如何验证？ |

不是所有维度都必须问到——只追问那些会影响实现方向、且用户没说清的。

### 4. 收敛判断

当继续提问的边际价值变低（关键边界都有答案、剩下的可以合理默认），**主动停止提问**。不要为了提问而提问；小改动可能 2~3 个问题就够了。

### 5. 输出澄清后的需求描述

把问答结果汇总成一份完整的需求说明，结构如下：

```
## 需求描述（澄清后）
- 目的：...
- 范围：做 ... ；不做 ...
- 约束：...
- 边界情况：...
- 成功标准：...
```

这份描述应当比用户的原始提示词显著更完整，足以让任何人（或任何 agent）据此直接实现。

### 6. 用户确认后才执行

输出需求描述后**停下来**，明确询问用户确认。用户要求修改就改完再确认；只有得到明确同意后，才进入实现阶段。

## 反模式

| 想法 | 现实 |
|---|---|
| 「这个需求够清楚了，直接做」 | 清楚是错觉。至少确认一次范围和不做什么。 |
| 「一次多问几个效率高」 | 一次一个问题，回答质量更高，也更容易随时转向。 |
| 「我替他假设一个合理默认值」 | 影响实现方向的假设必须问；只有无关紧要的细节才可默认。 |
| 「用户确认了大概方向，可以开工」 | 确认的是完整需求描述，不是「大概方向」。 |
