# git-commit v0.1.0

把当前工作区的变更整理为一组**原子提交**（atomic commits），每个提交只包含一个逻辑变更，消息遵循 Conventional Commits：**英文 type 前缀 + 中文描述**，如 `feat(auth): 增加登录重试`。

## 适用边界

- 适用：用户要求提交当前变更、整理提交历史前的落盘、为一段工作生成规范 commit。
- 不适用：push、rebase、amend、tag 等历史或远端操作——本 skill 只负责 commit，其他操作需用户单独明确要求。

## 工作流

### 1. 检查工作区

```bash
git status
git diff --stat        # 变更较多时先看概览
git diff               # 未暂存变更
git diff --cached      # 已暂存变更
```

同时看一眼 `git log --oneline -10`，了解仓库既有提交风格。若既有风格与 Conventional Commits 明显冲突（如全英文 free-form），先询问用户沿用哪种，再继续。

### 2. 制定提交计划

分析变更的逻辑边界，常见拆分维度：

- 功能 vs 重构 vs 格式化
- 不同模块 / 目录
- 实现 vs 测试 vs 文档（同功能的实现+测试应放在同一提交）
- 依赖升级 vs 行为变更

判断规则：

- 变更属于同一逻辑意图 → **一个提交**，不要为拆而拆。
- 混杂多个意图 → **拆分为多个原子提交**。
- 无法用一句话说清"改了什么、为什么" → 说明粒度有问题，重新划分。

把计划一次性呈现给用户确认，每组包含：**文件清单 + 拟用 type(scope) + 一句话说明**。用户认可后进入下一步；用户说"合成一个"就从简。

### 3. 逐组暂存与复审

每组只暂存属于本组的文件：

```bash
git add <file1> <file2>   # 禁止 git add . / git add -A
git diff --cached          # 复审将提交的内容
```

复审清单：

- 无密钥、token、`.env` 等敏感内容
- 无调试残留（`console.log`、`print`、注释掉的代码块等明显临时产物）
- 无与本组意图无关的改动混入

发现问题时停下来告知用户，不擅自"顺手修掉"。

### 4. 撰写提交消息

格式：

```text
type(scope): 中文描述

[可选 body：一段或要点列表，说明"为什么"而非复述"怎么改的"]

[可选 footer：BREAKING CHANGE: ... 或 Issue 引用]
```

规则：

- type ∈ `feat` / `fix` / `refactor` / `perf` / `docs` / `test` / `chore` / `ci` / `build` / `style` / `revert`
- scope 取模块或目录名，小写；难以归属时省略 scope
- subject ≤ 50 字符（中英文混排时按字符计），祈使语气，结尾不加句号
- body 仅在变更复杂或动机不明显时撰写
- **不添加任何 AI 署名**（无 `Co-Authored-By`、无 "Generated by" 字样）

### 5. 确认后执行

每组提交前把**暂存文件清单 + 消息草稿**展示给用户，确认后才运行：

```bash
git commit -m "$(cat <<'EOF'
type(scope): 中文描述
EOF
)"
```

- pre-commit hook 失败：如实报告失败原因并修复，**禁止 `--no-verify` 绕过**
- 全部组完成后，用 `git log --oneline -<N>` 展示结果摘要

## 反模式（禁止）

- `git add .` 一把梭，把无关变更混入提交。
- 为了拆分而拆分，把同一意图的实现和测试分到两个提交。
- 消息写成开发流水账（"先改了 A 再改了 B"），而不是最终状态与动机。
- 未经确认就执行 commit，或提交后顺手 push。
- 用 `--no-verify` 绕过失败的 hook 然后声称完成。
