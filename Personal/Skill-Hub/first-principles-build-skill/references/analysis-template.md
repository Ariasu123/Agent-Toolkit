# 第一性原理分析模板（Phase 1）

按以下 5 步执行分析，最终产出写入 `.fp-reviews/YYYY-MM-DD-<task-slug>-analysis.md`。

思维纪律（全程适用）：

- **区分物理与惯例**：每遇到一条限制，问"这是由问题本质/硬件/数学决定的，还是由历史、框架、团队习惯决定的？"只有前者不可挑战。
- **禁止类比推理**：推理链中不允许出现"业界都这么做""XX 项目就是这么实现的"作为论据。可以参考，但必须用本质事实重新论证。
- **警惕沉没成本与复杂度偏见**：已有代码、已学技术不是保留它们的理由；方案复杂不是它正确的证据。

## Step 1 — 问题本质

剥掉所有实现细节，回答：

- 用户真正要解决的问题是什么？（一句话）
- 不解决这个问题会怎样？（验证问题真实存在）
- 成功的可验证判据是什么？（具体到可以测试/观察）

## Step 2 — 假设审计

列出所有假设：任务描述中明示的、你脑补的、技术选型中隐含的。逐条挑战。

| # | Assumption（假设） | Challenge（挑战：物理还是惯例？证据？） | Verdict（成立 / 不成立 / 待验证） |
|---|---|---|---|
| 1 | | | |
| 2 | | | |
| 3 | | | |

规则：

- 至少 3 行；列不出 3 条假设说明任务太简单，不应走本流程。
- "待验证"的假设必须在 Phase 3 实现前用最小代价验证（读代码 / 跑一条命令 / 问用户）。

## Step 3 — 不可约事实（Ground Truths）

只保留不依赖任何框架、库、平台惯例就能成立的事实。每条标注来源：

- `需求`：用户明示
- `约束`：物理/数学/协议层面的硬限制
- `实证`：已通过代码/命令/文档验证的事实（附证据）

```text
GT1 [需求]  ...
GT2 [约束]  ...
GT3 [实证]  ...（证据：file:line / 命令输出）
```

## Step 4 — 向上推理

从 Ground Truths 出发重新构建方案：

1. 满足所有 GT 的最简方案是什么？（先假设零代码、零新依赖，逐步加回必要的复杂度）
2. 每一步增加的复杂度，对应哪条 GT 的要求？写不出对应 GT 的复杂度就是赘肉。
3. 给出最终方案的结构草图（模块/数据流/接口），以及明确**不做**的部分（YAGNI 清单）。

## Step 5 — 验证推理链

对方案中的每个关键决策做回溯检查：

| 决策 | 回溯到的 GT / 需求 | 还是惯例选择？ |
|---|---|---|
| | | |

- 回溯不到任何 GT 的决策：标记为"惯例选择"，写明为什么这个惯例在此场景仍然合理（允许，但必须显性化）。
- 发现推理断裂 → 回到 Step 4 修正方案，不要带伤进入实现。

## 输出文件格式

```markdown
# 第一性原理分析：<任务标题>
日期：YYYY-MM-DD ｜ 任务 slug：<task-slug>

## 1. 问题本质
## 2. 假设审计（表格）
## 3. Ground Truths（GT 清单）
## 4. 方案（结构草图 + YAGNI 清单）
## 5. 推理链验证（表格）
## 结论
一句话结论 + 是否推翻用户原设想（决定是否需要 Phase 2 确认）。
```
